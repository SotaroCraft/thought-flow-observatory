本書は、本プロジェクトの初回PoCにおいて「何を満たすべきか」を定義する正本である。詳細設計、関数・クラス設計、DDL、API詳細スキーマ、作り込んだUIモックは本書の対象外とし、次工程以降で本書に適合する形で決定する。

### 1.2 要求優先度

| 優先度 | 定義 |
|---|---|
| MUST | 初回PoCの成立または三軸評価に不可欠。原則として未達のまま完了扱いにしない |
| MUST NOT | 禁止事項。該当する実装・運用を行わない |
| SHOULD | 強く望まれる。期間・利用可否・費用などの制約で見送る場合は理由を記録する |
| COULD | 余力と価値が確認できた場合に実施する |
| OUT OF SCOPE | 初期MVPでは実施しない |

### 1.3 用語

| 用語 | 定義 |

| Captured | SourceをResearch Hubへ保存した状態 |
| Used | SourceをCopilotまたは分析で実際に利用した状態 |

| 解釈・仮説 | 観測事実を説明する候補。因果関係を確定するものではない |

## 2. 背景

通常の平均的トレンド分析では、大きな社会変化の初期兆候を捉えにくい可能性がある。本プロジェクトは、社会に現れる情報・文化・行動の分布と時間変化を複数の公開情報センサーから観測し、平均が大きく動く前に分散、偏り、多峰性などの分布形状が変化するかを小規模に検証する。

同時に、Microsoft 365、SharePoint Online（SPO）、Copilot、Microsoft Graph、Microsoft Entra ID、Azure、およびGCPを、公開情報を扱う一つのResearch Hubという実ユースケースへ自然に統合する。研究仮説が支持されない場合も、サービスの利用可否、制約、運用知見、クラウド比較、および再現可能な公開ポートフォリオを成果として残す。

## 3. 目的

### 3.1 目的A：Research Value

- 日・米・韓・中における「生成AI（Generative AI）」および「AI Agent / Agentic AI」の情報分布と伝播の差を観測する。
- 「どの指標が、どの領域・国・層で、平均変化より先に動くか」を優先的な研究問いとして検証する。
- 結果を「予想外 × 観測信頼性 × 価値」で評価する。
- 原因説明より先に、何が・どこで・誰に・いつ・どう変化したかを記述する。

### 3.2 目的B：Microsoft Practical Value / Career Evidence

- 公開情報向けAI Research HubをMicrosoft 365上に構築し、SPOをストレージ・可視化層、Copilotをコミュニケーション層、Graph / Entraを統合層として検証する。
- Microsoft 365 / Azure / GCPの実践的な利用可否、制約、採否判断を記録する。
- 第三者が目的から判断まで追跡できるPublic GitHub Repositoryを成果物とする。

## 4. 成功条件

### 4.1 Research

- **MUST** 日・米・韓・中 × 生成AI / AI Agentを対象に、少なくとも1つの再現可能な時系列分析を完了する。
- **MUST** 利用データ、テーマ辞書、国判定、集計方法、指標、対象期間を第三者が追跡できるようにする。
- **MUST** 仮説不成立や先行指標を発見できなかった結果も、条件と証拠を添えて正当な研究結果として残す。
- **MUST** 観測事実、解釈、原因仮説を区別する。

### 4.2 Microsoft

- **MUST** 研究専用SPO Research Hubが実環境で動作する。
- **MUST** Research Hub内の原典・Research Cardに対するCopilot利用を実環境で検証する。
- **MUST** Microsoft Graph / Entra IDによるSPO連携を最低限検証する。
- **MUST** Trialおよび契約で利用可能な候補機能について、可否、前提、制約、有用性、採否を記録する。
- **MUST** Microsoft 365の各採用機能が一つのResearch Hubにどう寄与したか説明できる。

### 4.3 Portfolio

- **MUST** Public GitHub Repository上で、第三者が「目的 → 設計 → 実装 → 検証 → 結果 → 継続 / 縮小 / 見送り判断」を追跡できる。
- **MUST** Secret、テナント固有情報、個人情報、業務機密、再配布権が不明なコンテンツを公開しない。
- **MUST** 研究結果が弱い場合でも、M365検証記録、クラウド比較、再現手順を独立した成果として残す。

## 8. 設計原則

1. **観測優先**：原因の断定より、測定可能な変化の記述と再現を優先する。
2. **測定方法の説明可能性**：何を、どのデータから、どの辞書・規則・指標で変化と判断したかを説明可能にする。
3. **使うために整理しない**：使った結果として整理される運用とし、未整理の蓄積を失敗としない。
4. **認知・操作コスト最小化**：MVPの多機能性より継続利用性を優先する。
5. **No-buildも成果**：既存サービスで十分な領域を再実装せず、見送り判断と根拠を成果に含める。
6. **研究基盤と専用Platformの分離**：Corpus、Research Hub、PoC分析基盤に集中する。
7. **疎結合**：SPO、Azure Blob、Azure AI Foundry、BigQuery、GitHub Actionsの停止・不採用時も、ローカルの基本分析を継続可能にする。
8. **三軸の残存価値**：Research / Microsoft / Portfolioのいずれかが弱くても、他の成果を失わない。
9. **公開前提の最小権限**：公開可能な情報のみ扱い、Secretや不要な固有情報を成果物から分離する。
10. **MVP統制**：新機能は、継続利用または検証価値が既存の構造化・運用コストを上回る場合のみ追加する。

## 9. 全体業務フロー / 通常運用フロー

```text
公開情報を発見
  ↓
Research HubへCapture
  ↓
最低限メタデータを自動 / 半自動取得
  ↓
Copilot等からそのまま利用可能
  ↓
実際に研究で利用
  ↓
継続価値がある資料のみResearch CardへPromote
  ↓
研究仮説・観測対象へ接続
  ↓
必要なら定量データ収集・分析
  ↓
結果をSharePoint Pages / Findingsへ戻す
  ↓
新しい問い
  ↺
```

### 9.1 運用規則

- **MUST** SourceのCaptureをResearch Card作成に依存させない。
- **MUST** 新規Source追加時の必須手作業を原則1操作以内とする。
- **MUST** Capture時にタグ、分類、要約の手入力を原則要求しない。
- **MUST** SourceはCapturedのままでもCopilot等から利用可能であることを検証する。
- **MUST** UsedおよびPromotedは実際の利用に基づく状態とし、単なる登録完了を意味させない。
- **MUST** 2週間利用しなかった後も、バックログ整理を要求せず再開できる。
- **MUST** 未整理Sourceの蓄積が通常利用を妨げない。
- **SHOULD** メタデータ取得や状態更新は、価値と実現可能性が確認できる範囲で自動化または半自動化する。

## 10. Phase構成

### 10.1 Phase 1A — Research Hub MVP

目的は、SPO Research Hubを立ち上げ、低負荷なCapture、Copilot利用、価値があるSourceだけのPromoteが成立するかを検証することである。

- **MUST** Sources Document Libraryを主たる原典保管・参照面として用意する。
- **MUST** Research Cardsを全Sourceの必須台帳にしない。
- **MUST** 最低限のPagesを用意する。
- **MUST** 3本のシード論文を通常運用フローに通す。
- **COULD** 初期はローカル生成物を手動でSPOへ投入する。

### 10.2 Phase 1B — SPO早期連携

Phase 1Aの価値確認後、Phase 2の本格化より不必要に遅らせず実施する。

- **MUST** Graph / EntraによるSPO接続の可否、必要権限、制約を実環境で検証する。
- **SHOULD** 価値が確認できた範囲でSourceまたは成果物の連携を実証する。
- **MUST** PnP等の特定技術を前提とせず、必要性に基づき採否を記録する。

### 10.3 Phase 2 — 思考潮流観測PoC

- **MUST** 2テーマ、4か国、4センサー系統を対象にデータ取得可能性を検証する。
- **MUST** 2022-11-30から初回実行日までをバックフィルする。
- **MUST** 初回実行後、2026-09-20まで週1回の差分更新を行う。
- **MUST** Rawを保持し、Canonicalを週次へ正規化する。
- **MUST** 分布形状と動態を用いる再現可能な分析を少なくとも1件完成する。
- **MUST** BigQueryで同一または同等分析を最低1回実施し、DuckDBと比較する。
- **SHOULD** ローカル週次運用の安定後にGitHub Actionsへ移行する。

## 12. データ要件

### 12.1 観測モデル

観測対象は次の7軸とする。

1. 情報 — 何が流れるか
2. 空間 — どこで広がるか
3. 人 — 誰が持つか
4. 時間 — いつ変わるか
5. ネットワーク — 誰から誰へ流れるか
6. 環境・適応 — 何が残存・消失に関係するか
7. 行動結果 — 最終的に何へ変換されたか

初期PoCの基本分析単位は **情報 × 人 × 空間 × 時間** とする。社会階層はmicro / meso / macro、時間尺度は短期 / 中期 / 長期、市場・地域の位置は先行 / 追随 / 後発として観測可能性を検討する。ただし、米国その他の特定国を常に先行市場とは定義しない。

### 12.2 対象テーマ・地理・期間

- **MUST** テーマは「生成AI」と「AI Agent / Agentic AI」の2つとする。
- **MUST** 国は日本、米国、韓国、中国とする。
- **MUST** 主分析期間は2022-11-30から2026-09-20までとする。
- **MUST** 初回実行時は2022-11-30から実行日までを取得対象とする。
- **COULD** 2022-11-30以前はベースライン補助に限り取得できるが、主分析期間とは区別する。

### 12.3 センサー

| 系統 | 初期候補 | 要件 |
|---|---|---|
| 研究 | OpenAlex、arXiv | **MUST** 少なくとも研究活動を観測可能な公開情報を検証する |
| 技術者 | GitHub | **MUST** 技術者活動を観測可能な公開情報を検証する |
| 企業 | 求人、企業IR、公式発表 | **MUST** 規約と技術的取得可能性を確認し、無理なスクレイピングを行わない |
| 一般関心 | Google Trends等 | **MUST** 国別の一般関心を観測可能な公開情報を検証する |
| SNS | 未採用 | **OUT OF SCOPE**。必要性が確認された場合のみ後続候補とする |

候補サービスは実装技術として確定したものではない。各系統で、利用可能性、規約、品質、再現性を確認して次工程で採用元を決める。

### 12.4 国判定

- **MUST** 厳格な一次属性のみを用いる。論文は著者所属機関の国、GitHubはOrganization / User profile等に明示されたLocation、企業は本社所在地、一般関心はサービスの対象国フィルタを原則とする。
- **MUST NOT** 氏名から国籍を推定しない。
- **MUST NOT** 言語から所在地を推定しない。
- **MUST NOT** LLMで不足プロフィールを補完しない。
- **MUST** 判定不能はunknownとして保持し、unknown比率をデータ品質指標として報告する。
- **MUST** 複数国所属などの元情報を保持し、集計規則を明示する。
- **TBD** 複数国所属の集計方式は分析目的に応じて次工程で決め、恣意的な変更を避けるため版管理する。

### 12.5 テーマ辞書

- **MUST** 各テーマについて日本語、英語、韓国語、中国語の用語を管理する。
- **MUST** 同義語、表記揺れ、除外語または誤検出防止条件を管理する。
- **MUST** 単独の `agent` など一般語による誤検出を避ける。
- **MUST** 辞書をGit管理し、いつ、どの語を対象にしたか再現可能にする。
- **MUST NOT** LLM意味分類を主判定に使用しない。
- **COULD** LLMを辞書候補や境界事例の補助検証に使用する。その場合、最終規則とAI出力を区別する。

### 12.6 Raw / Canonical

- **MUST** ローカル正本はDuckDB + Parquetとする。
- **MUST** Rawは取得元の粒度、原取得値、取得日時、データ源、対象期間、利用条件を可能な限り保持する。
- **MUST** Canonicalはセンサー横断比較のため週次へ正規化する。
- **MUST** Canonical生成でRawを破壊しない。
- **MUST** Rawと辞書・集計規則の版からCanonicalを再生成できる。
- **MUST** 欠損、unknown、取得失敗、仕様変更をゼロ値と混同しない。
- **SHOULD** 週次スナップショットまたは同等の差分追跡手段を保持する。

- DOI / URL

- Key Claims
- Evidence / Method

- Status
- 原典確認が必要な点

- **MUST** Cardは人間向けの圧縮知識であり、原典の代替でないことを明示する。
- **MUST** 原典または公開参照先をAIと人が再確認できるよう保持する。
- **MUST** Card作成をCaptureの前提にしない。
- **SHOULD** MVP項目は実利用に必要な最小限へ削減する。

## 15. 分析・研究要件

### 15.1 研究姿勢

分析は次の順で進める。

1. 観測
2. 変化・異常検出
3. 再現確認
4. 価値評価
5. 原因仮説
6. 必要な場合のみ因果検証

- **MUST** 原因を前提にセンサーや結果を選ばない。
- **MUST** 観測事実と原因仮説を明示的に分離する。
- **MUST** 仮説を支持しない結果を削除または失敗扱いしない。

### 15.2 主要指標

| 種別 | 指標候補 |
|---|---|
| 分布形状 | Mean、Variance、Skewness、Multimodality、Polarization、Concentration、Diversity / Entropy |
| 動態 | 増加速度、加速度、変曲点、持続期間、伝播遅延、必要に応じて再流行・半減 |

- **MUST** 平均値を基準比較に含める。
- **MUST** 分布形状または動態から少なくとも1指標を選び、平均変化との時間関係を検証する。
- **MUST** 指標の定義、入力、対象単位、欠損処理、比較方法を再現可能に記録する。
- **SHOULD** 複数の指標を用いる場合、探索的比較と確証的判断を混同しない。
- **TBD** MVPで採用する具体的指標、閾値、先行の判定幅、異常検出法はデータ品質確認後に決める。

### 15.3 初期仮説と研究候補

「大きな社会変化は、平均値が大きく動く前に、分散・偏り・多峰性などの分布形状変化として現れる可能性がある」を初期仮説とする。これは設計上の事実または成功条件ではない。

継続研究候補は次のとおりとする。

1. 平均より先に動く分布変化
2. トレンドセッターのさらに上流
3. 先行市場と後発市場の時間差
4. 観測技術そのものが潮流へ与える二次効果

Phase 2 MVPでは1を優先し、その他はデータ取得可能性と価値に応じて扱う。

### 15.4 既存研究の位置づけ

| 文献 | 役割 |
|---|---|
| Kashima et al. (2019), *The Psychology of Cultural Dynamics* | 流れの構造を考える理論レンズ |

- **MUST NOT** 3文献の登録自体を目的にしない。
- **MUST** 通常運用フローの初期シード / テストデータとして用いる。

依存関係上、SPOのTrial可否確認、BigQuery比較、コスト設定は期限リスクが高いため、後半へ集中させない。Azureの任意検証はMUST成果を阻害しない範囲で行う。

## 22. リスクと対策

| ID | リスク | 影響 | 対策・判断基準 |
|---|---|---|---|
| R-001 | 構造化や入力の負担が価値を上回り、利用されなくなる | Research Hubが形骸化 | Captureは原則1操作、Cardは選択的、2週間休止後の再開試験を受入条件にする |
| R-002 | Trial / ライセンス上、想定したM365機能が利用できない | Microsoft成果の縮小 | 可否確認自体を成果化し、手動SPO投入とローカル主系統を維持する |
| R-003 | Graph / Entraの権限または管理者同意が得られない | 自動連携不能 | 最小権限で早期検証し、阻害条件と代替運用を記録する |
| R-004 | 企業・一般関心データの規約、API、地域粒度が不十分 | 4センサー比較が不均衡 | 無理なスクレイピングをせず、代替候補・見送り・比較限界を明示する |
| R-005 | 厳格な国判定でunknownが多い | 国別比較の信頼性低下 | unknown比率を品質指標とし、補完推測せず、結論の適用範囲を制限する |
| R-006 | 多言語辞書の誤検出・漏れ | 国・テーマ比較の歪み | 辞書版管理、曖昧語の除外条件、サンプル検証を行う |
| R-007 | センサー間の量・定義・更新頻度が異なる | 横断指標の誤解 | Rawを保持し、Canonical規則、欠損、比較可能範囲を明示する |

| R-009 | 探索結果を因果として説明する | 誤った研究主張 | 観測、解釈、原因仮説を分離し、因果検証を後段に限定する |
| R-010 | Azure AI費用が予算を超える | 金銭的損失 | 1,000円上限、使用量記録、到達前判断、非AI代替を必須化する |
| R-011 | GCP Credit / Trial期限までに比較・判断が終わらない | 必須成果の未達 | 期限依存作業を前倒しし、2026-09-20より前に評価する |
| R-012 | Secretや再配布不可資料が公開される | セキュリティ・権利侵害 | データ分離、`.env.example`、公開前および履歴の検査、DOI / URL中心の公開とする |
| R-013 | 外部API仕様変更・停止 | 取得欠落、再現不能 | 取得ログ、Raw保持、センサー疎結合、手動・代替経路を維持する |
| R-014 | 機能追加が目的化する | 4週間でMUST未達 | 三軸への寄与と運用コストを追加条件とし、COULDを先に削る |
